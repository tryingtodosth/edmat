# EdMat — the 2026-09-19 update for webek4.fuw.edu.pl / edmat.net

## The one step the script cannot do: install the vhost

**`deploy/apache/edmat.conf` changed since the last applied bundle** (`4d8f371` — `text/javascript`
added to the `AddOutputFilterByType DEFLATE` list). Until it is installed, **no JavaScript on this
site is compressed**: measured live on 2026-09-17, the chemistry editor's chunk came down as
21,176,639 bytes with no `Content-Encoding` at all (it gzips to 6.9 MB), and the PDF worker's
`.mjs` as 1.26 MB the same way, while the HTML, CSS and API JSON beside them were all correctly
gzipped. See `UPDATE-2026-09-17.md` for the full measurement.

**`apply-on-server.sh` never writes into `/etc/apache2`, deliberately** (its step 4b says so: "the
installed vhost is reviewed by hand … the copy stays a deliberate, separate step"). What step 4b
does is diff the installed vhost against `$ROOT/deploy/apache/edmat.conf` and, when they differ,
print the commands below. **It compares against the copy the last bundle left on the server**, so
before this release's own rsync lands it would say "installed vhost matches" and stay silent about
a fix that only exists in the repo.

So the order matters, and it is the ordinary one:

1. Apply this bundle as usual. **Step 1's rsync of `deploy/` is what puts the fixed vhost at
   `~/todonet/deploy/apache/edmat.conf`** — no scp of a single file is needed, unlike the route
   `UPDATE-2026-09-17.md` describes for a server that had no bundle going out.
2. Step 4b will then genuinely warn and print what to run. Run it:

```bash
# on webek4, as todoonet, AFTER apply-on-server.sh has finished
diff /etc/apache2/sites-available/edmat.conf /home/todoonet/todonet/deploy/apache/edmat.conf
sudo cp /etc/apache2/sites-available/edmat.conf ~/edmat.conf.bak-$(date +%Y%m%d-%H%M%S)
sudo cp /home/todoonet/todonet/deploy/apache/edmat.conf /etc/apache2/sites-available/edmat.conf
sudo apache2ctl configtest && sudo systemctl restart apache2
```

**The diff is the gate, not decoration.** It should show one directive line and its comment block
and nothing else; anything more means the installed vhost has site-specific edits somebody made by
hand, and those must be carried across rather than overwritten.

Then confirm it actually took — the header is the whole point, and a `configtest` passing says
nothing about it:

```bash
# a real asset name, taken from the page — a glob in a URL is not expanded by the server
JS=$(curl -s https://edmat.net/ | grep -o '/_app/immutable/[^"]*\.js' | head -1)
curl -sI -H 'Accept-Encoding: gzip' "https://edmat.net$JS" | grep -i 'content-encoding'
# expect: Content-Encoding: gzip
```

## `/sitemap.xml` starts answering — no server step needed

`robots.txt` has been served from the frontend build for weeks and ends with
`Sitemap: https://edmat.net/sitemap.xml`, and the vhost already rewrites that exact path through to
Django. **Django had no such route, so the live URL 404s right now** (checked 2026-09-19) — the
frontend and vhost half of that pass merged and the backend half sat on a branch. This release
carries it, and the 404 becomes a real 789-URL sitemap with no further action.

**New optional setting, `EDMAT_PUBLIC_HOST`** — the hostname the sitemap builds absolute URLs
from, deliberately not the `Site` row (which still says `example.com`, since nothing ever set it;
it exists only because django-postman requires the sites framework). **It defaults to `edmat.net`,
so webek4 needs no `/etc/apache2/envvars` change at all.** Set it only if this ever runs under a
different public hostname. Verify after deploying:

```bash
curl -sI https://edmat.net/sitemap.xml | head -1            # expect 200, not 404
curl -s  https://edmat.net/sitemap.xml | grep -c '<loc>'    # expect ~789
```

## Message encryption: one new package, and one command you must decide about

**A new pip dependency, `cryptography`.** It is already in `backend/requirements.txt` in this
bundle, so `apply-on-server.sh`'s own `pip install -r requirements.txt` step installs it with no
extra action. Nothing in the standard library offers an authenticated cipher, which is why it is
here rather than hand-rolled.

**`EDMAT_MESSAGE_KEY` is optional and probably should stay unset.** Unset, the key is derived from
`SECRET_KEY` via HKDF, so a fresh deployment works with no setup. **The cost of that default,
stated plainly: rotating `SECRET_KEY` then makes every stored message unreadable.** If that is ever
on the cards, set `EDMAT_MESSAGE_KEY` (base64url of 32 bytes) in `/etc/apache2/envvars` FIRST, and
treat it as a backup-critical secret from then on.

**`manage.py encrypt_messages` converts the messages already in the database, and is deliberately
NOT run automatically.** It is not a data migration on purpose: a migration would encrypt every row
under whatever key happened to resolve at migrate time on every deployment, including one whose key
was not set up yet — and getting that wrong makes messages unreadable rather than merely
unencrypted, long after the migration that caused it. A mixed table is a normal, supported state:
rows written before this release keep reading, because `decrypt_text` returns an unprefixed value
unchanged.

So, after the bundle is applied and confirmed working:

```bash
cd /home/todoonet/todonet/backend
.venv/bin/python3 manage.py encrypt_messages --check    # says what it would do, changes nothing
.venv/bin/python3 manage.py encrypt_messages            # idempotent; safe to re-run
```

**Do not run it before the step-0 backup has been confirmed on disk.**

## Traceability — read this before trusting `MANIFEST.txt`

**This bundle was packed from a working tree that carries uncommitted work**, the same way
`UPDATE-20260917` was, so its manifest names `a9311fb` and that commit does not contain all of it.
What is committed: the server-performance work, the sitemap, gzip, the exercise-page changes and
the inline-picture feature. What is NOT: galleries, governor applications and message encryption
were finished and verified by their author but not yet committed when this was packed.

The consequence is narrow and worth knowing: the payload is correct and complete (pack.sh rsyncs
the tree, not `git archive`), but it cannot be reproduced from git, and a rollback of the CODE
means re-rsyncing the previous bundle's `backend/` and `frontend/build/` rather than checking out
a commit. `FUW/UPDATE-20260917.tar.gz` is that previous bundle and is still on disk. The step-0
database backup remains the rollback for the migrations either way.

**`main` had also diverged from `origin/main` at pack time** (23 ahead, 7 behind, where all 7 are
duplicate-SHA twins of commits already in local history — origin is a strict content subset). The
push was refused as a non-fast-forward and was deliberately not forced. Nothing about that affects
this bundle; it affects where these commits end up afterwards.
