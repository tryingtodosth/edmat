## The one step the script cannot do: install the vhost

**`deploy/apache/edmat.conf` changed since the last applied bundle** (`4d8f371` — `text/javascript`
added to the `AddOutputFilterByType DEFLATE` list). Until it is installed, **no JavaScript on this
site is compressed**: measured live on 2026-09-17, the chemistry editor's chunk came down as
21,176,639 bytes with no `Content-Encoding` at all (it gzips to 6.9 MB), and the PDF worker's
`.mjs` as 1.26 MB the same way, while the HTML, CSS and API JSON beside them were all correctly
gzipped. See `UPDATE-2026-09-17.md` for the full measurement.

**`apply-on-server.sh` never writes into `/etc/apache2`, deliberately** (its step 4b says so: "the
installed vhost is reviewed by hand … the copy stays a deliberate, separate step"). What step 4b
does is diff the installed vhost against `$ROOT/deploy/apache/edmat.conf` and, when they differ,
print the commands below. **It compares against the copy the last bundle left on the server**, so
before this release's own rsync lands it would say "installed vhost matches" and stay silent about
a fix that only exists in the repo.

So the order matters, and it is the ordinary one:

1. Apply this bundle as usual. **Step 1's rsync of `deploy/` is what puts the fixed vhost at
   `~/todonet/deploy/apache/edmat.conf`** — no scp of a single file is needed, unlike the route
   `UPDATE-2026-09-17.md` describes for a server that had no bundle going out.
2. Step 4b will then genuinely warn and print what to run. Run it:

```bash
# on webek4, as todoonet, AFTER apply-on-server.sh has finished
diff /etc/apache2/sites-available/edmat.conf /home/todoonet/todonet/deploy/apache/edmat.conf
sudo cp /etc/apache2/sites-available/edmat.conf ~/edmat.conf.bak-$(date +%Y%m%d-%H%M%S)
sudo cp /home/todoonet/todonet/deploy/apache/edmat.conf /etc/apache2/sites-available/edmat.conf
sudo apache2ctl configtest && sudo systemctl restart apache2
```

**The diff is the gate, not decoration.** It should show one directive line and its comment block
and nothing else; anything more means the installed vhost has site-specific edits somebody made by
hand, and those must be carried across rather than overwritten.

Then confirm it actually took — the header is the whole point, and a `configtest` passing says
nothing about it:

```bash
# a real asset name, taken from the page — a glob in a URL is not expanded by the server
JS=$(curl -s https://edmat.net/ | grep -o '/_app/immutable/[^"]*\.js' | head -1)
curl -sI -H 'Accept-Encoding: gzip' "https://edmat.net$JS" | grep -i 'content-encoding'
# expect: Content-Encoding: gzip
```

### The branch has diverged from `origin/main` — resolve this before packing

At the time of writing this checkout is **17 ahead, 6 behind**, and the six on the far side are the
SAME patches under different SHAs (`ca41aab` is this checkout's `a1e8d35`, `8d97f1f` is `0428ac9`,
and so on) — somebody pushed the same work from elsewhere. So the divergence is duplicate history
rather than divergent content, and a two-dot diff of the tips confirms it: **`backend/` and
`frontend/` are byte-identical between them.** The only real differences are this deploy work —
these two runbooks, the vhost fix, and a handful of one-line edits to older `UPDATE-*.md` files
that exist on origin and not here.

What that means for packing: **a bundle from this checkout ships the same application code as
origin plus the vhost fix**, so there is no regression risk in packing from here. What it does
mean is that `git push` will refuse until somebody reconciles the two. `git rebase origin/main`
drops the duplicate patches on its own and leaves only the commits origin genuinely lacks, but it
rewrites local history, so it is the account owner's call and not something to do on the way past.
