# Integrating the logbook prototype with EdMat

How the single-school logbook prototype becomes a module of the EdMat platform, how it runs as a public demo that collects feedback, and how it stays bilingual. Written for the EdMat product and engineering team.

## 1. What "integrated with EdMat" should mean

The prototype is a complete, self-contained application: one Node process, one JSON store per school, its own login, its own UI. EdMat as a platform will want to present it as **one product module among several** (logbook, courses, meetings, later: library, canteen, HR) that share identity, look and navigation. Three integration levels are possible, from cheapest to deepest; the prototype now supports the first two, and the third is a matter of configuration plus a small amount of platform code.

| Level | What the platform does | What the prototype provides today |
| --- | --- | --- |
| **A. Linked** | Lists the logbook as a product, links to a school's instance | Runs anywhere with `npm start` or the Dockerfile; per-school data volume |
| **B. Embedded** | Mounts the logbook under the school's EdMat site (`/dziennik`), signs users in from the platform, shares the design system | `EDMAT_BASE_PATH` (assets, API and service worker all prefix-aware), `EDMAT_SSO_SECRET` + `GET /api/auth/sso?token=…` (signed, expiring, replay-protected hand-off), the same `window.EdMat` bundle and tokens as the design system |
| **C. Composed** | Renders logbook screens inside a platform shell, with platform-wide messaging and identity | The screen registry (`EdApp.screen`) and module registry (`server/modules.js`) are the seams: each screen is a self-registering classic script, each feature area is a module that can be switched off per school |

The recommended path is B now and C when the platform has its own shell. Everything below assumes B.

### The module contract

- **Identity.** The platform is the identity provider. It mints `login`/`email` + `exp` + `nonce` tokens with the shared secret; EdMat maps them to local accounts by login or e-mail and inherits roles from the local account (roles must exist in EdMat; the platform can provision them through the registrar API). Local passwords stay for schools without a platform account, and 2FA/password policy stay local.
- **Modules.** `GET /api/modules` lists modules with `pl`/`en` names and `enabled`; `PATCH /api/admin/modules` toggles them. Disabled modules return `404 module_disabled` and disappear from navigation. Required modules (core, logbook, grades, registrar, messages) cannot be disabled.
- **Time.** School logic runs on the school's wall clock, not the container's: `Europe/Warsaw` by default, `TZ`/`EDMAT_TZ` per process, `config.timezone` per school. A platform that starts the container must set `TZ` (the shipped `Dockerfile` does), otherwise "today", homework deadlines, cut-offs and quiet hours drift by an hour or a day. Clients send local wall times; the server stores ISO instants with the offset.
- **Pupil-record scope.** One gate decides who may read a pupil's grades, remarks, submissions and descriptive assessments: `D.assertMayReadPupilRecord(db, user, studentId, kind)`. The pupil, a guardian with scope `full`, a teacher who teaches that pupil, the homeroom teacher, the principal and the support team read them; care, cafeteria, library, nurse and the DPO keep the pupil directory and the day's attendance only. A guardian's effective scope is now derived from their **parental-authority status** (`full` / `limited` / `deprived` / `court-restricted`), which a platform provisioning accounts must set together with the legal basis — an explicit `accessScope` only narrows what the status already allows, never widens it (`D.guardianScope`, `docs/GUARDIANS.md`). The same scope gates messages, notifications and every consent decision, not only reads.
- **Configuration a client sees.** `GET /api/auth/session` ships an **allowlist** of config keys (`server/index.js` `PUBLIC_CONFIG_KEYS` / `PUBLIC_PUSH_KEYS`: school, year, timezone, demo/setup flags, messaging and visibility switches, `adultAccess`, session timeouts, homework/test limits, the help video, plus the push mode and the public VAPID key). Anything not on that list — video provider secrets, `ipAllowlist` and its explanatory strings, payroll rates, the retention table, the school private key, the security posture keys — never leaves the server. A platform adding a config key must add it to the allowlist deliberately; the default is "not public".
- **Data ownership.** One instance = one school = one data directory (`data/school/`: one JSON file per collection, an append log for the hot ones and `files/` for the bytes that are not documents — the § 22 archive packages and signature files, `docs/STORAGE.md`; `scripts/backup.js` turns the whole lot, `files/` included, into a single `.json.gz` bundle while the server runs). Nothing leaves the process except what the school exports (SIO XML, payroll CSV/XML, print-ready HTML and the PDFs rendered from it). No third-party scripts, fonts or analytics are loaded, which the test suite verifies (`[3.9.8]`). The one deliberate exception is a school that configures its **own** video host: the CSP is then widened to exactly that hostname and `public/app/screens/meetings.js` lazily loads `https://<host>/external_api.js` from it. That host is the school's (or its authority's) own server, never a third party — see `docs/VIDEO.md` §5.3–§5.4. With no video host configured, nothing outside this process is ever fetched.
- **The statutory year.** A school year here ends on **31 August**, and § 22 of the school-records regulation counts its ten days from that date, not from the last day of teaching (`config.archiveWindow.from` / `.yearEnd` / `.days` override both). A platform that schedules anything around "year end" — a tenancy rollover, a data export, a decommissioning — must not do it before the year's archive package exists and is signed: after 31 August the school still holds the August resit results and the promotion resolutions that close the year. `docs/ARCHIVE.md` carries the open legal question and the three signature states (`digest-matched` = signed, `stored-unverified`, `accepted-unverified` = an audited decision of the head teacher). Nothing leaves the process except what the school exports (SIO XML, payroll CSV/XML, print-ready HTML and the PDFs rendered from it). No third-party scripts, fonts or analytics are loaded, which the test suite verifies (`[3.9.8]`). The one deliberate exception is a school that configures its **own** video host: the CSP is then widened to exactly that hostname and `public/app/screens/meetings.js` lazily loads `https://<host>/external_api.js` from it. That host is the school's (or its authority's) own server, never a third party — see `docs/VIDEO.md` §5.3–§5.4. With no video host configured, nothing outside this process is ever fetched.
- **Events.** The append-only audit log is the integration event source: `GET /api/principal/audit` with filters, plus per-module lists. A platform that wants push semantics should poll it (a webhook can be added in `server/lib/audit.js` in one place).
- **Look.** The design-system bundle is copied verbatim into `public/edmat/`. When the platform updates the design system, it republishes the bundle and tokens; nothing in the prototype's screens depends on component internals.

## 2. Demo for feedback

Demo mode (`EDMAT_DEMO=1`, module `demo`) turns an instance into an evaluator sandbox without weakening the real security model:

- **Role switch without passwords.** `POST /api/demo/switch` creates a session for one of thirteen personas (teacher, homeroom, principal, psychologist, counsellor, registrar, admin, student, parent, care, cafeteria, library, nurse). The login page lists them; the demo bar switches between them mid-session. Real logins keep working.
- **What to try.** `GET /api/demo/guide?role=…&locale=…` returns the checklist stories for that role in Polish or English, with a badge on every story that has an automated test. Evaluators therefore see the same acceptance list the team works from.
- **Feedback.** `POST /api/feedback` stores rating, kind (bug, idea, praise, question), text, contact, current screen, role and locale. Principals and admins read it at `GET /api/feedback` and export it as CSV. Feedback survives `POST /api/demo/reset`, which reseeds everything else.
- **Reset.** Any evaluator damage is undone by a reset; the seed is deterministic ("today" is 23.10.2026) so guided scenarios stay reproducible.

**Rollout suggestion.** Host one public demo instance per language (`?lang=pl`, `?lang=en`) behind the EdMat site, with a weekly automatic reset, and a private instance per pilot school seeded with their own timetable import (`POST /api/admin/timetable/import` — an aSc XML export, an Optivum publication folder, CSV or JSON, with the two-phase entity mapping and an undoable batch; `docs/IMPORT.md`). Feedback CSVs from both feed the same backlog.

**A demo instance is not a pilot instance.** A pilot school runs **one statutory logbook and only one** — see `docs/PILOT.md` § 0. A platform must therefore never present the demo and the school's own instance as interchangeable, and never provision a second instance for the same school "to try things out with real classes".

## 3. Two languages

- **UI.** Every screen carries a `pl` and `en` dictionary; the shell, bundle components and formatting (dates, decimal comma, currency) switch with `A.setLocale`, which is stored on the user's account (`users[].locale`) and in the browser. `?lang=en` in the URL forces a language, which is also how SSO tokens carry a locale.
- **Data.** School data is Polish by nature (statuses ob/nb/sp, grade categories, legal document text). The English UI translates labels around it and leaves official printouts Polish, because those are the legal documents. A school running in English (international schools) would translate its own category names in the category manager; the codes stay.
- **Server messages.** Error messages come from the server in Polish with a stable `code`; the client shows the message. If an English-only deployment is needed, the codes are the hook for a client-side translation table.

## 4. Courses and meetings

The two new modules extend the same seams: `courses` (a lightweight LMS: units, items, quizzes with auto-grading, assignments reusing homework, discussion, progress and certificates) and `meetings` (self-hosted video with Jitsi Meet or BigBlueButton behind a provider abstraction, JWT hand-off from EdMat, recording consent, attendance from provider events). See `docs/COURSES.md` and `docs/VIDEO.md`. Both are optional modules a school can switch off.

## 5. What stays out of scope for a prototype

- A bundled PDF engine. PDFs **are** produced when a headless Chromium happens to be installed on the host (`GET /api/pdf?path=…`, `server/lib/pdf.js`, `EDMAT_CHROME`); the prototype simply does not ship one, and falls back to print-ready HTML with `501 pdf_unavailable` when it is missing.
- Qualified electronic signatures. The archive seal is a real RSA-SHA256 seal of the school's own key, not a qualified one; and the signature the head teacher attaches afterwards is only **digest-checked** against the package — the logbook validates no certificate chain and never calls a signature qualified (`docs/ARCHIVE.md`).
- XSD validation of the SIO package. `POST /api/registry/sio/validate` runs the school's own structural self-check and says so in the answer (`schema: not-validated-against-cie-xsd`); the CIE schema is not shipped (`docs/SIO.md`).
- Multi-school hosting in one process (by design: one node per school keeps data separation trivial; a platform runs many nodes).

Push delivery is **no longer** on this list: Web Push (RFC 8030/8291/8292) ships with no npm dependency, off by default (`POST /api/push/config`), carrying only `{v, kind, id, ts}` to the push service while the device fetches the wording from the school (`docs/PUSH.md`). Two consequences a platform must carry: the school acquires a **sub-processor outside the EEA** the moment push is switched on (Google's FCM, Apple's APNs), which the processing agreement has to name; and the notification the device then shows is deliberately neutral for the kinds that would otherwise put a pupil's name on a lock screen.
