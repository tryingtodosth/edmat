Prototype · one school, one process

A school logbook that belongs to the school

EdMat is an electronic logbook for Polish primary and secondary schools: attendance, grades, classification, substitutions, the support team, the registrar, messages, courses and school modules, all in one dependency-free Node process on the school's own server. This page says what works, what is simulated, what is open and how to join. The demo runs in this same installation.

Open issues, read before judging

  1. No teacher, parent or pupil has touched it. Every “works” below means “passes a test written by the same kind of model”.
  2. No real school file has been seen yet: the aSc, Optivum and pupil-list importers were tested on reconstructed formats.
  3. The signature on the year-end archive (§ 22): the code accepts five kinds and does not rule which one suffices. A question for a lawyer, not a developer.
  4. No external penetration test and no DPIA by a lawyer. The security review was a model reading a model.
  5. The JSON store is right for a pilot of about 150 pupils, not the 600 in the brief. The SQLite swap behind the same Store API is described, not done.

Why

Pupil data never leaves the school's server. One Node 18 process per school, zero npm dependencies, a JSON store with append logs and a one-command backup. No trackers and no third-party origins in the CSP; one of the tests guards that.

For whom

Teacher, homeroom teacher, principal, counsellor and psychologist, registrar, administrator, data protection officer, pupil, parent (including a divorced pair with separate accounts), after-school care, cafeteria, library and nurse. Every role has its own screen in Polish and English; official documents stay in Polish.

How it was built

The acceptance criterion is a list of 145 user stories: each has a test carrying its number, and the coverage report counts only green tests with no SKIP directive. Three review rounds found 126 defects in the first version (20 blockers, 5 security-high) and 25 weak tests; a research round followed. The code is about 50,000 lines and documented, but your team did not write it. Whoever inherits it must decide whether to own it.

What it does, role by role

Each card is one screen of the logbook and a few checklist stories behind it.

Teacher

  • attendance in one click, drafts and an offline queue
  • grades with weights, plus/minus, retakes and np/bz; weighted averages
  • lesson topics against the curriculum, homework, materials and courses

Homeroom teacher

  • classification, proposed grades, semester locks
  • certificates and record sheets on MEN blanks, A4 printouts
  • excuses, remarks, notices to parents with read receipts

Principal

  • substitutions, overtime, payroll export
  • pedagogical supervision and an append-only audit log
  • the § 22 year-end archive as a package for an external signature

Support team

  • IPET, WOPFU, opinions and decisions
  • notes encrypted for named readers (RSA-OAEP + AES-GCM)
  • an alert after three days of absence of a supported pupil

Registrar and administrator

  • the pupil register, PESEL or identity document, name change with a legal basis
  • timetable import from aSc and Optivum, an SIO package with its own structure check
  • modules, four-eyes retention, TOTP, an IP allowlist

Pupil

  • timetable, homework, tests, courses and quizzes
  • own grades and attendance, pupil rights
  • an adult pupil decides about the parent's access

Parent

  • two children on one account, a profile switcher
  • e-excuses, messages, push notifications with no content on the lock screen
  • parental-authority status decides what the other parent sees

School modules

  • after-school care, a cafeteria with payments, trips, library, nurse
  • courses (a small LMS) with quizzes and a certificate
  • video meetings on a self-hosted Jitsi

What is real and what is simulated

Most of it is real. Here is exactly what is not.

Real

  • passwords (scrypt), TOTP, session timeout, brute-force limits, IP allowlist
  • encrypted specialist notes and the archive seal
  • Web Push with end-to-end encryption (RFC 8291, test vector byte for byte)
  • PDFs from a real Chromium when one is installed
  • per-collection store with append logs, crash recovery, backups
  • PESEL checksum, SIO XML, payroll CSV/XML, print-ready documents
  • audit log: append-only, frozen rows, a retention job

Simulated or never run for real

  • the qualified electronic seal is an RSA seal with the school key, not a qualified service
  • payments are recorded, no payment operator is connected
  • video: the Jitsi integration is built but never run against a real server
  • push: encryption and VAPID tested, never sent through a real browser push service
  • the SIO package is not validated against the CIE XSD, and the response says so
  • “today” in the demo data is pinned to 23.10.2026; a blank install uses the clock
  • the school data is synthetic; Primary School No. 12 in Kraków does not exist

The next four weeks

  1. Week 1A usability session with three teachers and two parents on the demo instance; every hesitation recorded. Fix what the session shows.
  2. Weeks 1–2Import one real aSc or Optivum timetable export and one anonymised pupil list; fix the importers against reality.
  3. Weeks 2–3A legal read of retention, consent, access rules and the archive signature (§ 22); a penetration test of the auth surface.
  4. Weeks 3–4Decide storage; if the 600-pupil brief stands, swap to SQLite behind the same Store API before any pilot.
  5. Any pilotOne statutory logbook per school, no double entry: either the school switches with the gmina's consent, or it pilots satellite modules only.

Known product gaps

  • the registrar's pupil-list import is dry-run only; there is no apply step
  • the certificate prints the nominative although the declension forms are collected
  • the archive package is an uncompressed ZIP: 48 MB for a 600-pupil year
  • no scheduler: reminders and clean-up are raised by a request or by cron

Discussion and feedback

Feedback is collected in the demo: the “Give feedback” button on the demo bar stores a rating, a kind (bug, idea, praise, question), the text and the screen it came from. The principal and administrator export it as CSV. There is no forum or public comments here, deliberately: this is a project page, not a portal.

Who we are looking for

  • Lawyerurgent

    § 22 and the signature kind, parents' access to an adult pupil, consents, retention. Four of the fourteen decisions wait for this person.

  • Pilot schoolurgent

    One real timetable export (aSc or Optivum) and an anonymised pupil list. Without it the importers are proven only on reconstructions.

  • Data protection officerimportant

    Read the DPIA template, the processing agreement and the retention table; decide whether push ships in the pilot at all.

  • School archiveimportant

    JRWA categories for thirteen documentation classes are marked unverified. Every school has its own list.

  • Teachers and parents for a sessionopen

    An hour with the demo, a screen recording, every hesitation noted. The first real “I don't get it” is worth more than another review round.

  • Accessibility testeropen

    Screen reader, 200 % zoom, high contrast, keyboard only. The automated tests exist; the human ones do not.

  • Penetration testeropen

    The auth surface, sessions, TOTP, uploads, SSO. So far the review was a model reading a model.
