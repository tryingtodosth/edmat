# Brief: backend ports on four branches, one source of truth, and a discussion thread on every page

**Status: design only — nothing below is built.** Dictated by the project owner and refined in one
question round; every decision marked **(owner)** came from them directly, everything else is
analysis they are free to overrule. Written as a handover for later sessions, like `NAVBAR-BRIEF.md`
was. Committed on the navbar branch only so it is not lost; the work itself starts from fresh
branches off `main`.

The four decisions already made **(owner)**:

1. The ports reimplement **the whole REST API backend** — not just a render pipeline.
2. The single source of truth is a **language-neutral spec plus a golden test corpus**.
3. Discussions attach to **every page, keyed by URL** — WordPress-style, one thread per page.
4. This session delivers **the design document only**.

---

## 1. Honest scale, before anything else

Measured on the real repo, not estimated: **580 registered URL patterns** (including the Django
admin and DRF format suffixes — the real API surface a port must answer is roughly 150–200
operations), **16 Django apps**, **1084 backend test functions**, plus subsystems that are not
"just JSON over SQL": token auth, cache-backed throttling, an SSE stream, multipart uploads with
libmagic content-sniffing, Pillow image re-encoding (the avatar pipeline is a *security boundary*,
§17Q), a ClamAV socket, django-postman's third-party tables, the Nominatim proxy with its global
1-req/s gate, bleach sanitization, per-locale content resolution, and the telemetry log shards.

A full-parity port is **months of work per language**, and every future Django feature then costs
4× to ship everywhere. That cost does not go away by planning; the design below contains it two
ways: ports track **tagged spec versions, not main's tip** (§4), and each port advances through
**milestones** (§6) so a branch is useful long before it is complete. Given the budget
constraint this project lives under, the recommended reading of this whole brief is: build §7
(discussions) and §3 (the spec) first — they are cheap and useful even if no port ever ships —
and treat the ports as long-running background experiments, Go first.

## 2. The branch model (owner: one branch per language, one as-is)

- **`main`** — the Python/Django backend, unchanged, and **permanently authoritative**: it is the
  only place the schema, the spec, and new features are ever authored.
- **`port/go`**, **`port/rust`**, **`port/c`** — long-lived branches. Each adds a sibling
  directory (`backend-go/`, `backend-rust/`, `backend-c/`) and **touches nothing else** — the
  frontend, `backend/`, and `spec/` arrive by merging `main` in, one way, regularly. A port branch
  never edits `spec/`; a port that needs the contract changed changes Django on `main` first, which
  regenerates the spec, which the port then merges. That one-way rule is what keeps four
  implementations from becoming four opinions.
- The frontend needs exactly one accommodation, already built: `PUBLIC_API_BASE_URL` is the one
  switch that points it at whichever implementation is running. No frontend fork.

## 3. The source of truth (owner: spec + golden corpus)

The "template mechanism" in EdMat is worth naming precisely, because it is what the ports must
reproduce: the backend's contract is **JSON over HTTP** — all human-visible rendering
(Markdown+LaTeX → KaTeX HTML) happens client-side in `renderContent.ts` and is already pinned by
`npm run check:katex`. So the source of truth for a backend port is the JSON the reference
implementation emits, captured mechanically:

- **`spec/schema.sql`** — the SQLite DDL, exported from Django (`sqlite3 db.sqlite3 .schema` after
  a clean `migrate`). Ports run against **the same schema**; Django remains the sole migration
  authority. This is the single decision that makes even a C port conceivable: a port is a
  stateless HTTP layer over a schema it never owns.
- **`spec/endpoints.json`** — the operation inventory (method, path, auth, throttle scope, feature
  flag), generated by a new management command that walks Django's own URL resolver — the API
  introspecting itself, so the artifact cannot drift from the code that serves it.
- **`spec/golden/`** — the corpus: recorded (request → expected response) pairs, generated by a new
  `dump_golden_corpus` command replaying a scripted scenario set (browse, search, auth, submit,
  moderate, book, message, …) against a freshly seeded reference database. Volatile fields
  (tokens, timestamps, autoincrement ids) are normalized at record time, the same way the existing
  e2e scripts already stamp and clean their data.
- **`spec/conformance/`** — one language-neutral runner (Node, since the repo already drives e2e
  in Node): boot any implementation on a port, load the seed fixture, replay every golden, diff
  JSON structurally, print the same `ok`/`FAIL` lines every e2e script here prints. **A port's
  definition of done at any milestone is "the runner passes its milestone's goldens" — the same
  runner, all four implementations, no per-language test suites to keep in sync.**
- **Versioning**: `main` regenerates the spec whenever the API changes and tags it
  (`spec-v1`, `spec-v2`, …). A port declares which tag it conforms to; drift is a failing
  conformance run after a merge, surfaced mechanically rather than discovered by a user.

## 4. What a whole-backend port actually contains (the hard-parts inventory)

In rough order of pain, with the honest note per item:

| Subsystem | Portability |
|---|---|
| JSON CRUD over SQLite (taxonomy, exercises, materials, study, community…) | Straightforward in all three languages; the bulk of the surface. |
| Token auth + throttles | Easy (token lookup; counter in memory/SQLite — the Python one is per-process LocMemCache anyway). |
| Search/filters (`?q=`, visibility layers) | Careful SQL translation; goldens catch every mistake. |
| SSE notification stream | Easy in Go, fine in Rust, manual in C; poll-loop design ports as-is. |
| Multipart uploads + libmagic sniffing | All three bind libmagic; C natively. |
| Image re-encode (avatars, event-post pictures) | Go: `image/*`; Rust: `image` crate; **C: this is a security boundary — bind a maintained library or exclude uploads from the C milestone rather than hand-rolling decoders.** |
| ClamAV socket | Trivial socket protocol everywhere. |
| django-postman messaging | No library exists elsewhere — port the *tables* (they are in `schema.sql`) and reimplement the thread logic (~200 lines; the reply-linking rules are documented in §17P). |
| Nominatim proxy + global 1 req/s gate | Simple; the gate is a mutex. |
| Sanitization (bleach) | Go: bluemonday; Rust: ammonia; **C: no maintained equivalent — sanitize-on-read stays the frontend's DOMPurify, and the C milestone must not accept HTML writes until this is answered.** |
| Django admin | **Not ported, ever.** Admin work happens on `main`; it is an authoring tool, not API surface. |

## 5. Language notes

- **Go** — the cheapest port and the recommended first: stdlib `net/http` + `database/sql` +
  `mattn/go-sqlite3`, single static binary, `bluemonday`, SSE natively. Best effort-to-result
  ratio for a solo student.
- **Rust** — axum + sqlx (or rusqlite), `ammonia`, `image`. Steeper, but the compiler carries the
  correctness load; second.
- **C** — libmicrohttpd (or mongoose) + `sqlite3.h` + libmagic. The most expensive and the most
  instructive; the milestones below deliberately let the C branch stop at read-only and still be a
  complete, honest artifact. Third, or never — say so in the branch README rather than leaving it
  half-implied.

## 6. Milestones (each branch, in order — conformance-runner-defined)

- **M0** — boots, serves `/api/disciplines/` from the seeded DB, passes its first golden.
- **M1** — the whole *anonymous read* surface: browse, detail, search, feature flags. (This is the
  majority of real traffic and makes the port demoable behind the real frontend.)
- **M2** — auth + the ordinary writes (reviews, comments, sets, submissions).
- **M3** — the hard tail: uploads, SSE, messaging, booking, moderation. Full parity.

## 7. The per-page discussion (owner: every page, keyed by URL) — buildable now, on `main`

Independent of the ports, and deliberately built in Django **first** so it enters the spec and the
goldens like everything else, and every port inherits it as contract rather than as an idea.

- **Model**: one new row kind, `community.PageThread(path unique, created_at)` — `path` is the
  frontend pathname, normalized (no query string except none at all; the homepage's `?tab=` views
  are one page, one thread). Comments attach through the **existing** generic
  `Comment(content_type, object_id)` — the same mechanism exercises, materials and coverage claims
  already use, so threading, tombstones, reporting (`kind='comment'`) and moderation all come free.
  `check_auto_hide` already no-ops gracefully for targets without a viewer pool (the
  MaterialCoverage precedent).
- **API**: `GET /api/pages/thread/?path=/foo` (public read, returns the thread's comments,
  creating nothing), `POST` same path (authenticated, get-or-creates the `PageThread`, then the
  comment; `parent` validated against the same thread — the §17O cross-target rule). Path
  validation: must start `/`, no scheme/host, length-capped — it is untrusted input that becomes a
  lookup key, never HTML.
- **Kill switch**: a new `FeatureFlag('page_discussions')`, seeded on, gating both actions —
  the standing convention (§17T), including the links/panel disappearing with it.
- **Frontend**: one `PageDiscussion.svelte` rendered from the root layout under every page,
  **collapsed by default** ("Discussion about this page (N)") — WordPress puts comments at the
  foot of the page and so does this; reuses `DiscussionThread`/`CommentNode` unchanged. Both
  locales in the same change, as always.
- **Deliberately not**: no per-API-endpoint threads (the owner chose pages), no separate comment
  system (one `Comment` model remains the only one), no threads on pages behind auth walls being
  publicly readable — the thread endpoint answers for the *path*, so the read is public exactly
  like the page list itself; a path that leaks private content in its text is the commenter's own
  writing, same as any public comment today.

## 8. Build order, and what each step costs

1. **Page discussions** (§7) — one session. Useful today, port-independent.
2. **The spec + conformance runner** (§3) — one to two sessions. Useful even with zero ports: the
   golden corpus is a regression net `main` itself currently lacks at the HTTP layer.
3. **`port/go` M0–M1** — a few sessions. First real payoff: benchmarks and a second opinion on the
   contract (recording goldens will surface undocumented behavior — expect spec fixes on `main`).
4. **`port/rust` M0–M1** — after Go proves the harness.
5. **`port/c`** — last, explicitly optional, milestone-capped at M1 unless the answers in §4's C
   rows change.
6. M2/M3 per branch only if the experiment earns it.

## 9. Risks, stated rather than implied

- **The 4× tax is permanent** for any feature that must reach parity — mitigated only by the
  spec-tag policy (ports lag deliberately) and by capping milestones.
- **Golden brittleness**: over-strict diffs (ordering, float formatting) will cry wolf; the runner
  must diff structurally with per-endpoint normalization rules from day one, or it will be muted
  and then it is not a source of truth.
- **Schema coupling**: ports reading Django's schema means a Django migration can break every port
  at once — that is the *correct* failure mode (loud, at conformance time), but it means port
  branches must merge `main` regularly, not annually.
- **Security surfaces do not port for free**: the upload/image/sanitization boundaries were each
  hard-won on `main` (§17N/§17Q); a port that skips one silently is worse than no port. The
  milestone gates in §4/§6 exist for exactly this.
